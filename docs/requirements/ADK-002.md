# ADK-002 — Trusted Autonomous Engineering Pipeline

## 1. Objective

在 ADK-001 已建立的 Windows MVEE 基礎上，建立可信任、可驗證、具備強制工程約束的自主工程交付管線。

本次 Requirement 必須解決以下已確認的工程能力缺口：

- 缺少 GitHub Actions CI。
- Independent Review 無法完整自主執行驗證。
- Agent Eval 覆蓋範圍及證據強度不足。
- Agent 直接於 main Branch 開發及推送。
- 缺少強制性的 Pull Request、Review 與 Merge Integration Gate。

ADK-002 為 Athena Pilot 的必要前置里程碑。

在 ADK-002 完成驗收前，不得開始 Athena 產品開發。

## 2. Engineering Principles

延續 ADK-001 的所有工程原則、治理政策、Architecture、Engineering Standards、Feature Map、Implementation Integrity 及 Engineering Trust Pyramid。

不得以增加 Prose Instruction 作為解決工程約束問題的唯一方式。

應優先透過架構、平台原生機制、Static Analysis、Verification 及可執行的 Integration Gate 建立強制約束。

不得降低 ADK-001 已建立的工程品質。

## 3. Baseline Assessment

自主探索目前 ADK Repository、原始需求、ADR、Feature Map、工程能力、Skills、GitHub 設定、驗證紀錄及已知限制。

確認：

- 目前 Branch 與 Remote 狀態。
- GitHub Repository 權限。
- Branch Protection 或 Ruleset 狀態。
- GitHub Actions 可用性。
- Program 與 Review 的 Runtime 及認證方式。
- 現有 Verification Gate 的適用範圍。
- Agent Eval 的案例、評分方式及證據來源。
- Windows Independent Review 的執行限制。
- 現有工程工具是否存在僅適用於 ADK 自身的硬編碼限制。

保存實際基線及能力缺口。

## 4. Bootstrap Branch Governance

ADK-002 自身必須開始採用 Branch-based Development。

在進行正式專案內容修改前：

- 確認本地與遠端 main 狀態。
- 保存目前基線 Commit。
- 從最新且已確認的 main 建立獨立工作分支。
- 所有 ADK-002 實作、文件、測試及相關修改均於工作分支進行。
- 不得直接將開發成果 Commit 或 Push 至 main。
- 建立 Pull Request 作為正式整合入口。

若完整 Integration Gate 尚未建立，應保持 PR 未整合狀態，直到必要條件具備。

不得以 Bootstrap 為理由繞過最終整合條件。

## 5. Branch and Pull Request Governance

建立通用的 Branch-based Engineering Workflow。

每項工程任務應具備：

- 可追溯的 Requirement 或 Task Identity。
- 明確的 Base Commit。
- 獨立工作分支。
- 具有工程意義的 Commit。
- Pull Request。
- Verification Evidence。
- Independent Review Result。
- Integration Decision。
- 最終版本紀錄。

應研究適當的 Branch Naming、Commit Convention、PR Metadata 及版本追溯方式。

Agent 應自主處理分支建立、提交、推送、PR 建立、一般衝突修正及版本確認。

不得要求專案負責人提供一般工程操作指令或手動傳遞 Commit SHA。

## 6. Protected Main Branch

研究並建立適當的 GitHub Branch Protection 或 Repository Ruleset。

main 必須受到平台層級的工程約束。

必要約束包括：

- 禁止一般開發流程直接 Push 至 main。
- 必須透過 Pull Request 整合。
- 必須通過必要的 CI Status Checks。
- 必須具備獨立審查核准或經核准的等效強制審查機制。
- 新 Commit 必須使舊版本核准失效。
- 禁止 Force Push。
- 禁止未經授權的 Branch Deletion。
- 禁止 Agent 自行繞過、停用或削弱保護規則。

應實際驗證保護規則的有效性，而非僅確認設定存在。

涉及 Repository 安全政策、權限及治理變更時，須取得專案負責人的必要核准。

## 7. GitHub Continuous Integration

建立可重現的 GitHub Actions CI。

CI 應使用已核准的工程工具，實際執行適當的：

- Engineering Policy Checks。
- Feature Map Validation。
- Comment Policy Enforcement。
- Architecture Dependency Validation。
- Ruff Formatting。
- Ruff Lint。
- mypy Type Checking。
- Software Verification。
- Gitleaks Secret Scanning。
- 其他已建立且適用的工程檢查。

CI 必須針對實際待整合版本執行，並保存可追溯的驗證證據。

應研究 GitHub-hosted Runner 與現有 Windows 工具鏈的相容性。

不得因現有 Git 或 Gitleaks 的固定安裝路徑及執行檔雜湊限制，而直接停用安全驗證。

若現有工具設計不適合 CI，應研究並建立具有等效或更高安全保證的可重現方案。

CI 失敗時必須阻止 Merge。

不得使用虛假的成功狀態、無實際驗證內容的 Workflow 或跳過必要檢查的方式取得通過。

## 8. Independent Review Environment

分析 ADK-001 中 Windows 執行政策限制 Reviewer 的根本原因。

建立能夠獨立取得及驗證工程證據的 Review Environment。

Reviewer 必須能在合法授權範圍內自主取得：

- 原始 Requirement。
- Repository 內容。
- Base Commit。
- Target Commit。
- 實際 Git Diff。
- Architecture。
- Feature Map。
- Engineering Standards。
- ADR。
- CI 結果。
- 必要測試及執行證據。

Reviewer 不得完全依賴 Program 提供的摘要或自行宣告的驗證結果。

Reviewer 應具備獨立執行必要驗證的能力。

應優先解決合法的環境、工具及隔離配置問題，不得繞過 Runtime Sandbox 或安全限制。

Review Environment 應保持唯讀的正式原始碼存取邊界，必要的測試及暫存寫入應於隔離環境進行。

## 9. Agent Identity and Authorization

研究 Program 與 Review 在 GitHub 上的 Identity、Authentication 及 Authorization 分離方案。

候選方案可包含 GitHub CLI、獨立 Bot Identity、GitHub App、GitHub Actions 或其他成熟方案。

應比較：

- Identity Isolation。
- Least Privilege。
- PR Approval Capability。
- Merge Capability。
- Credential Management。
- Security。
- Maintenance Cost。
- Runtime Compatibility。
- Auditability。
- GitHub Ruleset Compatibility。

不得假設不同 Codex Session 等同不同 GitHub Identity。

不得以 Program 的自我核准取代 Independent Review。

若使用非原生 PR Approval 的機器審查機制，必須證明其獨立性、不可任意偽造及平台強制效果，並取得治理核准。

新增外部服務、認證機制、權限及重大架構決策須依 Governance 流程取得核准。

## 10. Role Responsibilities

維持 Program、Review、Research 三種主要角色。

Program 負責：

- 需求探索。
- 建立工作分支。
- 實作。
- Local Verification。
- Commit and Push。
- 建立 Pull Request。
- 修正 CI 與 Review 發現的問題。

Review 負責：

- 獨立取得工程證據。
- 審查實際版本。
- 執行必要的獨立驗證。
- 判斷需求、架構、測試及實作完整性。
- 提出阻擋性 Finding。
- 核准符合條件的版本。
- 授權符合 Integration Gate 的 Merge。

Research 負責技術研究、候選方案比較、工程問題調查及決策證據。

不得新增沒有實際必要性的 Agent Role。

Merge 的執行應由可驗證的整合機制完成，不得僅依賴 Agent 的自然語言判斷。

## 11. Integration Gate

建立可執行、可測試、可追溯的 Integration Gate。

Merge 前必須確認：

- PR 來自合法工作分支。
- Base 與 Target 版本符合整合政策。
- PR Head SHA 與驗證目標一致。
- 必要 CI Checks 全部通過。
- Independent Review 核准目前 Target。
- 不存在未解決的阻擋性 Finding。
- 不存在未核准的重大技術決策。
- 不存在 Merge Conflict。
- 符合 Branch Protection 或 Ruleset。
- Merge 操作具備合法授權。

任何必要條件缺失、失敗、過期或無法驗證時，均不得 Merge。

Integration Gate 必須採 Fail-closed 行為。

應處理驗證與 Merge 之間的版本變更風險，避免使用舊版本的核准結果整合新版本。

Merge 完成後應自主確認實際整合結果、main Commit 及必要的版本證據。

## 12. Review and Correction Loop

CI 或 Review 失敗時，應將可定位的工程證據及 Finding 提供給 Program。

Program 應自主：

- 分析根本原因。
- 研究必要解決方案。
- 修正實作。
- 執行 Local Verification。
- 更新 Commit。
- 更新 Pull Request。

更新版本後應重新執行必要的 CI 及 Independent Review。

不得沿用不適用於新版本的核准結果。

應避免無限修正循環，建立合理的失敗分類、進度保存及阻礙升級機制。

一般修正不得要求專案負責人介入。

## 13. Agent Evaluation Expansion

擴充 ADK-001 的 Agent Eval 基線。

至少涵蓋以下能力領域：

- Feature Discovery。
- Architecture Compliance。
- Autonomous Verification。
- Autonomous Recovery。
- Self-documenting Code。
- Implementation Integrity。
- Problem Evasion Detection。
- Independent Review Accuracy。
- Correct Approval。
- Governance Compliance。
- Branch Governance。
- CI Failure Handling。
- Stale Review Detection。
- Integration Gate Enforcement。
- Autonomous Merge。
- Session Recovery。
- Honest Failure Reporting。

Agent 應自主設計具備實際工程意義的案例。

案例應包含正常、異常、邊界及刻意違規情境。

應區分：

- Software Verification。
- Deterministic Gate Tests。
- Agent Behavioral Evals。
- End-to-end Engineering Evals。

不得將單一案例的多個評分欄位誤計為多個獨立案例。

## 14. Evaluation Integrity

Agent Eval 應優先使用實際 Runtime、Git、GitHub、工具輸出及可驗證的工程證據。

不得僅以受評估 Agent 的自述作為通過依據。

應建立獨立的評估條件及適當的未見案例。

不得讓受評估 Agent 擅自修改驗收標準、預期結果或評分器以取得通過。

應評估重複執行的一致性，保存失敗結果及必要的改善證據。

Reviewer Eval 必須同時評估缺陷辨識能力與正確核准能力，避免全面拒絕或全面核准。

應依實際成本、風險及案例特性提出合理的評估規模與通過標準。

## 15. Security and Governance

維持 ADK-001 的所有安全及治理要求。

特別注意：

- Program 不得自行取得 Reviewer 的認證憑證。
- Reviewer 不得修改被審查的正式原始碼。
- Agent 不得擅自修改自身的權限及保護規則。
- 不得自行降低 Required Status Checks。
- 不得偽造 CI 或 Review 結果。
- 不得透過修改測試、Workflow、Gate 或 Eval 逃避工程約束。
- CI 與治理相關修改應受到適當的獨立審查。
- 不得將憑證或敏感工程資訊提交至 Public Repository。
- 不得執行未經授權的外部資料傳輸。

應研究如何避免 Program 同時控制待審查程式碼及其全部驗收機制。

涉及權限擴張、付費服務、Repository Ruleset 或重大架構變更時，必須取得必要核准。

## 16. Observability and Feedback

擴充既有工程觀測及介入紀錄。

應能追蹤：

- Requirement 與 Task。
- Program、Review Session。
- Branch。
- Pull Request。
- Base 與 Target SHA。
- CI Run。
- Verification Result。
- Review Finding。
- 修正輪次。
- Integration Decision。
- Merge Result。
- Human Intervention。
- Engineering Failure。
- Improvement Candidate。

不得捏造 Runtime 未提供的資料。

應利用實際失敗改善工程環境，優先將重複性問題委派至架構、Static Analysis 或 Verification。

## 17. Progressive Dogfooding

ADK-002 必須使用自身建立的工程能力完成開發。

已完成且通過驗證的能力應立即應用於後續工作。

ADK-002 最終必須透過 Branch、Pull Request、CI、Independent Review 及 Integration Gate 完成正式整合。

不得在完成管線後改以直接 Push main 的方式交付 ADK-002。

## 18. Autonomous Execution

專案負責人僅提供需求、重大決策及必要治理授權。

Agent 應自主完成：

- Repository 探索。
- 技術研究。
- 工作包拆分。
- Branch Management。
- 檔案及資料夾建立。
- 工具安裝及設定。
- 程式實作。
- Workflow 建立。
- 測試與 Debug。
- Commit and Push。
- Pull Request。
- Review。
- 問題修正。
- Integration。
- 專案知識維護。
- 最終驗收。

不得要求專案負責人執行 Agent 可以自主完成的一般工程操作。

遇到真正需要治理決策的事項時，應提供證據、候選方案、推薦理由、風險及所需核准範圍。

部分工作受阻時，應繼續其他不受影響且已獲授權的工作。

## 19. Acceptance Criteria

### Branch Governance

- ADK-002 使用獨立工作分支開發。
- 正式成果透過 Pull Request 整合。
- main 具備實際有效的保護規則。
- 已驗證未經授權的直接 Push 無法成功。
- Agent 無法任意繞過保護規則。

### Continuous Integration

- GitHub Actions 已實際執行。
- 必要工程檢查具備真實驗證內容。
- 正常版本可以通過 CI。
- 刻意違規版本會使 CI 失敗。
- CI 失敗時無法 Merge。

### Independent Review

- Reviewer 使用獨立 Session。
- Reviewer 能自主取得實際版本及工程證據。
- Reviewer 能獨立執行必要驗證。
- Program 不得自我核准。
- 審查結果具備明確版本追溯。

### Agent Evals

- 已建立涵蓋必要能力領域的實際案例。
- 已執行正常、異常及未見案例。
- 已建立合理的通過標準及可重播證據。
- 已評估 Reviewer 的缺陷辨識及正確核准能力。
- 已記錄失敗及改善結果。

### Integration Gate

- 未通過 CI 的 PR 無法 Merge。
- 未通過 Review 的 PR 無法 Merge。
- 過期的 Review 不得授權新版本 Merge。
- 存在阻擋性 Finding 時無法 Merge。
- 所有必要條件通過後，Agent 能自主完成 Merge。
- 不需要專案負責人手動核准一般 PR 或執行 Merge。

### End-to-end Engineering

至少完成一項真實工程任務的完整閉環：

Requirement → Branch → Implementation → Local Verification → Commit → Push → Pull Request → CI → Independent Review → Correction → Integration Gate → Merge → Feedback。

另須驗證正常交付、CI 失敗、Review 拒絕、版本變更及未授權整合等必要情境。

所有刻意違規案例應於適當隔離環境進行，不得污染正式 main。

## 20. Definition of Done

只有在所有必要驗收條件均已滿足，且具備實際執行證據時，才能宣告 ADK-002 完成。

不得將文件、Placeholder、模擬成功結果或尚未執行的 Workflow 視為完成。

不得以人工 Merge 取代自主整合能力的驗收。

若 Runtime、GitHub 權限、認證或其他必要條件仍存在阻礙，必須明確記錄為 Blocked 或 Partial。

不得在 ADK-002 尚未完成驗收時開始 Athena Pilot。

最終報告應包含：

- 實際架構及工具選型。
- ADR 與核准紀錄。
- Branch Protection 實際狀態。
- GitHub Actions 執行證據。
- Independent Review 環境及權限邊界。
- Agent Identity 設計。
- Integration Gate 實作及驗證結果。
- Agent Eval 結果。
- 完整 PR Lifecycle 證據。
- 正常及違規情境驗證結果。
- Human Intervention Analysis。
- 已知限制及剩餘風險。
- ADK-001 Regression Verification。
- Athena Readiness Assessment。

所有成果應更新至適當的 Feature Map、Architecture、Engineering Standards、Workflow、ADR 及其他專案知識。

文件及報告使用繁體中文，技術識別碼、API、Schema、Git Metadata 及程式碼使用適當的英文。

## 22. Execution

將本 Requirement 保存至 Repository，並依現有工程規範開始自主執行。

首先建立 ADK-002 工作分支，再進行正式開發。

除必要治理決策外，不得等待專案負責人提供逐步工程指令。
